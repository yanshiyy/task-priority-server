# 任务委派功能 · 开发需求说明

> 适用版本：**多用户服务器版**（`task-priority-server/`），仅此版本实现。
> 目标用户：user1–user5（5 个已注册账户，全部账户可互派）。
> 状态：**已实现并部署**（2026-08-22；API 30 项 + DOM 11 项测试通过）。

---

## 一、功能目标

在"任务优先级决策器"的多用户版本中，实现**任务在用户之间流转委派**的完整闭环：

1. **委派发起**：任一用户可将自己的一个任务委派给其他用户；
2. **任务积压提示**：委派人自身任务积压时提示是否考虑委派（分流引导）；
3. **来源可见**：被委派人的任务列表中出现委派任务，并明确显示**任务来源人**；
4. **执行反馈**：被委派人可对委派任务提交执行情况反馈（进行中 / 遇阻 / 已完成 + 文字说明）；
5. **确认闭环**：委派人收到反馈后进行确认（确认完成 / 退回重做），形成闭环；
6. **二次转发**：被委派人收到多个委派任务时，可将其中任务**再转发（二次委派）**给第三人。

---

## 二、角色与权限

| 角色 | 可做 | 不可做 |
|---|---|---|
| **委派人**（from 用户） | 发起委派、查看反馈、确认完成、退回重做、撤回（仅未反馈时） | 修改已委派任务的评分字段 |
| **被委派人**（to 用户） | 查看委派任务、提交反馈、二次转发（转派） | 确认/退回（那是委派人的动作） |
| **第三人**（二次转派的接收者） | 同"被委派人" | — |
| **其他人**（无关用户） | 不可见该委派记录 | 不可操作 |

> 权限判定全部在**服务端**强制校验（不能只靠前端隐藏）。

## 三、业务流程

### 3.1 发起委派

```
委派人（user1）
  └─ 任务卡片 → 点「委派」按钮
      ├─ 若"今天必做"类任务 ≥ 3 个 → 弹出提示：
      │    "您当前有 N 个任务积压，是否考虑委派部分任务以减轻负担？"
      │    [继续委派] [暂不]
      ├─ 选择被委派人（下拉：user2~user5，排除自己）
      ├─ 填写委派说明（可选，默认携带原任务标题与备注）
      └─ 确认 → 服务端创建委派记录
           ├─ 原任务在 user1 列表中变为「已委派 · 待反馈」状态（锁定，见 3.5）
           └─ 被委派人（user2）下次刷新即见该任务（来源：user1）
```

**触发条件**：仅"待办/进行中"且**未委派**的任务可发起委派；"已完成/已阻塞/已委派"不可。

### 3.2 被委派人查看

- user2 登录后，任务列表出现委派任务卡片，显著标识：
  - 徽章：**来源：user1**（来源人用户名，以颜色区分"委派/自建"）；
  - 卡片显示委派说明；
  - 评分沿用委派时的快照（重要度/紧急度/难度/P 值冻结，与委派时一致）；
  - 卡片按钮组变为：`✓ 完成` `反馈` `转派` `编辑` `删除`（**不显示"委派"**，防止重复委派；删除仅移除自己列表中的副本）。

### 3.3 执行反馈（被委派人 → 委派人）

被委派人点「反馈」，提交：
- **状态**（三选一，必选）：
  - 进行中（doing）
  - 遇阻 / 需要帮助（blocked）
  - 已完成（done）
- **文字说明**（可选，≤200 字）；
- 服务端记录反馈时间，委派状态置为 `feedback`。

> 完成反馈：被委派人侧任务标记为"已完成（待委派人确认）"，但**委派人侧原任务不自动完成**——必须等委派人确认（见 3.4）。

### 3.4 确认闭环（委派人）

- user1 收到反馈后（列表出现未读角标 + 卡片状态"待确认"），点「查看反馈」：
  - 看到：被委派人姓名、反馈状态、反馈文字、反馈时间；
  - 两个动作：
    - **确认完成** → 委派状态 `confirmed`；**user1 原任务自动标记完成**；user2 侧任务同步"已确认完成"；
    - **退回重做** → 委派状态回 `active`，被委派人可继续修改并再次反馈（可多次往返）；
- 附带确认意见文字（可选）。

### 3.5 已委派原任务锁定

user1 侧原任务显示状态徽章 `已委派给 user2 · 待反馈/待确认`：
- 不可直接点"完成/编辑评分"（评分已快照，若想改需先**撤回**）；
- 可操作：`撤回委派`（仅当被委派人尚未反馈）、`查看反馈`、`确认/退回`（收到反馈后）。

### 3.6 二次转发（转派）

- 被委派人 user2 收到委派任务后，可点「转派」→ 选择第三人 user3 → 确认；
- 服务端新建一条委派记录（from=user2, to=user3），**保留原始来源链**：
  - user3 看到的"来源"显示为 **user1**（最原始委派人），同时标注"经 user2 转派"；
- 原委派（user1→user2）状态同步为 `re-delegated`（user1 侧显示"已转派给 user3"）；
- 反馈与确认闭环沿最新委派（user2→user3）进行；user1 侧显示最终结果。

### 3.7 撤回

- 委派人在被委派人**尚未反馈**时可撤回 → 委派取消，原任务恢复可编辑；
- 已反馈/已确认的不可撤回（只能走退回重做）。

## 四、数据模型

### 4.1 新增表 `delegations`（SQLite）

```sql
CREATE TABLE IF NOT EXISTS delegations (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  from_user_id   INTEGER NOT NULL,            -- 委派人（当前链上的发起方）
  to_user_id     INTEGER NOT NULL,            -- 被委派人
  root_user_id   INTEGER NOT NULL,            -- 最原始委派人（转派链追溯）
  parent_id      INTEGER,                     -- 上一级委派 id（转派时非空；NULL=原始委派）
  task_snapshot  TEXT NOT NULL,               -- 委派时刻任务完整快照 JSON（评分冻结）
  source_title   TEXT NOT NULL,               -- 原任务标题快照（冗余，便于展示）
  note           TEXT DEFAULT '',             -- 委派/转派说明
  status         TEXT NOT NULL DEFAULT 'active',
                 -- active(待执行) | feedback(已反馈待确认) | confirmed(已确认完成)
                 -- | rejected(退回重做) | cancelled(撤回) | re-delegated(已转派)
  feedback_status TEXT,                       -- 最新反馈：doing | blocked | done
  feedback_note   TEXT,                       -- 最新反馈文字
  feedback_at     INTEGER,
  confirm_action  TEXT,                       -- confirm | reject
  confirm_note    TEXT,
  confirmed_at    INTEGER,
  created_at      INTEGER NOT NULL,
  updated_at      INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_deleg_to    ON delegations(to_user_id, status);
CREATE INDEX IF NOT EXISTS idx_deleg_from  ON delegations(from_user_id, status);
CREATE INDEX IF NOT EXISTS idx_deleg_root  ON delegations(root_user_id, status);
```

### 4.2 任务对象扩展字段（前端任务 JSON）

- 委派人侧原任务新增：
  ```json
  {
    "...原字段": "...",
    "delegated": { "delegationId": 1, "to": "user2", "status": "active" }
  }
  ```
- 被委派人列表中出现的委派任务（服务端合成，非落库到其 tasks blob）：
  ```json
  {
    "id": "deleg-<id>-<taskId>",      // 合成 id，避免与本机任务冲突
    "title": "<原标题>",
    "a": ..., "b": ..., "c": ..., "cMode": ..., "due": ..., "cManual": ..., "estMin": ...,
    "status": "todo",
    "delegatedFrom": "user1",          // 来源人
    "reDelegatedBy": "user2",          // 转派链上的人（可选）
    "delegationId": 1,
    "note": "<委派说明>"
  }
  ```

## 五、API 设计（服务端）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/delegations` | 返回我发起 + 我接收的委派列表（含状态/对方/未读标记） |
| POST | `/api/delegations` | 发起委派 `{ taskId, toUsername, note }`（服务端读取该用户任务并快照） |
| POST | `/api/delegations/:id/feedback` | 被委派人反馈 `{ status: doing|blocked|done, note }` |
| POST | `/api/delegations/:id/confirm` | 委派人确认 `{ action: confirm|reject, note }` |
| POST | `/api/delegations/:id/redelegate` | 转派 `{ toUsername, note }` |
| POST | `/api/delegations/:id/cancel` | 撤回（仅 active 且未反馈） |
| GET | `/api/tasks`（扩展） | 响应追加 `delegated`（委派给我的任务快照数组）与 `delegationAlerts`（未读数） |

**统一校验**（服务端强制）：
- 所有委派接口需登录；
- 只有 `to_user_id` 本人可 feedback / redelegate；
- 只有 `from_user_id`（或 root 链上委托人）可 confirm / cancel；
- 转派时接收者不能是自己；不能转派回来源链上已有的人（防环）。

**响应格式约定**（示例）：
```json
// GET /api/delegations
{
  "mine":   [{ "id":1, "to":"user2", "title":"...", "status":"feedback", "feedbackStatus":"done", "feedbackNote":"...", "feedbackAt":..., "unread": true }],
  "assigned": [{ "id":1, "from":"user1", "rootFrom":"user1", "reDelegatedBy":"", "title":"...", "status":"active", "note":"..." }],
  "alerts": { "newAssigned": 2, "newFeedback": 1 }
}
```

## 六、前端交互设计（`public/app.js` / `index.html` / `styles.css`）

### 6.1 委派入口
- 顶层任务卡片操作区新增按钮：**委派**（仅非已委派/未完成/未阻塞任务）。
- 设置页增加「委派中心」入口（或顶部铃铛角标）：查看"我委派的 / 委派给我的"。

### 6.2 委派抽屉（发起）
- 字段：被委派人下拉（其余账户）、委派说明（可选）、原任务摘要；
- 提交前若"今天必做"任务 ≥3 → 先弹积压提示（可"继续委派/暂不"）；
- 成功提示 + 刷新。

### 6.3 委派任务卡片（被委派人视角）
- 徽章 `来源：user1`（品牌色）；若经转派加 `经 user2 转派`；
- 操作：`✓ 完成`（提交"已完成"反馈）、`反馈`（三态+文字）、`转派`、`编辑`（仅备注/说明）、`删除`（仅移除本端视图）；
- 卡片角标提示新到达委派（未读数）。

### 6.4 反馈抽屉（被委派人）
- 三态单选 + 文字说明 + 提交。

### 6.5 确认视图（委派人）
- 收到反馈后卡片显示 `待确认` 徽章 + 铃铛角标；
- 查看反馈 → 显示反馈内容 → [确认完成] [退回重做] + 意见文字。

### 6.6 转派抽屉（被委派人）
- 选择第三人 + 说明；确认后刷新，原卡片状态变"已转派"。

### 6.7 角标与轮询
- 顶部「委派」图标显示未读数（新委派 + 新反馈）；
- 前端每 30 秒静默轮询 `/api/delegations` 更新角标（与现有 400ms 防抖保存互不干扰）。

## 七、边界与异常处理

| 场景 | 处理 |
|---|---|
| 委派时被委派人不存在 | 400 错误提示 |
| 委派给自己 | 400 拒绝 |
| 转派成环（A→B→A） | 400 拒绝（校验 root 链） |
| 撤回时对方已反馈 | 403，提示只能"退回重做" |
| 已确认后任何一方再操作 | 403 状态已终态 |
| 委派任务被被委派人删除 | 仅移除其视图，委派记录不受影响（可重新出现在刷新后？——约定：删除后不再显示，委派记录保留） |
| 双方同时操作（乐观锁） | 委派记录以服务端状态机为准，状态变更用条件更新（WHERE status=期望值），冲突返回 409 提示刷新 |
| 被委派人侧任务 id 冲突 | 合成 id `deleg-<id>-<taskId>` 保证唯一 |

## 八、测试计划

### 8.1 API 集成测试（`test/api.test.js` 扩展）
1. user1 委派给 user2 → user2 的 GET /api/tasks 出现委派任务且含 `delegatedFrom=user1`；
2. 未登录访问委派接口 → 401；
3. 无关用户 user3 操作该委派（feedback/confirm）→ 403；
4. user2 feedback(done) → 状态 feedback；user1 confirm → 状态 confirmed，user1 原任务自动完成；
5. 退回重做：reject → 状态回 active，user2 可再次反馈；
6. 转派：user2 → user3，user3 见来源 user1 + 经 user2 转派；user1 原委派变 re-delegated；
7. 撤回：active 时 cancel → cancelled，原任务恢复可编辑；已反馈时 cancel → 403；
8. 环检测：转派给来源链上的人 → 400；
9. 乐观锁/并发：两次 confirm 第二次 → 409；
10. 角标未读数：新委派/新反馈后 alerts 数值正确。

### 8.2 前端 DOM 冒烟测试（`test/dom.test.js` 扩展）
1. 任务卡片出现「委派」按钮（非已委派任务）；
2. 发起委派 → 原卡片出现"已委派"徽章、按钮禁用；
3. 被委派人视角渲染"来源：user1"徽章；
4. 反馈抽屉提交 → 委派状态更新；
5. 委派人确认视图出现反馈内容与两个动作按钮；
6. 任务积压提示：≥3 个今天必做时发起委派弹出提示。

## 附录：已确认的业务决策

| 决策项 | 结论 |
|---|---|
| 多重任务提示场景 | A. 委派人任务积压时提示（今天必做≥3）+ C. 被委派人收到多项时可再转发（转派） |
| 委派后原任务去向 | A. 保留并锁定为"已委派"（可撤回/确认/退回） |

| 委派范围 | A. 全部已注册账户可互派（user1–user5） |
